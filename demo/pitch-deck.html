The risk isn’t the version number

An override with no recorded reason is the migration risk

/* OV-05c: header cells carry the slate-900 brand weight,
   not Material's grey — brand review, Mar 2023 */
.bofa-table .mat-header-cell { color: $boa-slate-900; }

Material renames the internal class between majors. The selector dies silently. The intent — a brand decision someone signed off — is now unenforced, and nothing in the repo knows.

Migrating a design system is migrating intent, not selectors.

One is a diff. The other is a sentence a reviewer can act on.

Where it failed — the slide that should buy your trust

  • The pixel budget was 0.1% of pixels. It waved a wrong brand red through to a customer dashboard. Now 40 absolute pixels.
  • The first dark-theme check asserted the light-theme colour: two of five transaction rows rendered at 1.07:1 — unreadable balances — and the suite was green.
  • The intent gate’s first run found three dead overrides in our own library; one was passing only because Material’s default happened to equal the brand colour.
  • A migration run explained its own red screenshots as a missing-font problem. It wasn’t. The gate held; the narrative failed.
Found by adversarial review, not by design — and all of it written down in the repository.

What the agent did, and did not, do

  • Two independent runs of the same playbook both left CI red on the snapshots Material’s MDC rewrite changed — and neither regenerated a baseline to get green.
  • Both stopped on the same ambiguous override with the same reasoning. That reasoning was wrong; human review caught it, not a test.
  • Against a third-party design system with zero intent comments: 3 genuine stops, 1 false stop, and three confident wrong guesses no gate caught.
It does not guess when it knows it doesn’t know. It does not yet know when a confident rewrite has quietly stopped applying — so the intent gate is pilot scope, not a nice-to-have.

Controls, in your language

  • The output is a pull request. It inherits every control you already have — CODEOWNERS, branch protection, your scanners.
  • No baseline change without a written reason. CI rejects the PR body without BASELINE-CHANGE:, and the guard cannot be edited by the PR it guards.
  • npm ci --ignore-scripts as policy: no transitive lifecycle script runs before a human reads the diff.
  • Renderer pinned by digest, so “it passed on my machine” is not evidence.
  • Every session is a replayable transcript: prompt, commands, diffs, approvals.

Why an examiner prefers this to a person doing it

“Who changed the customer-facing control, on what evidence, reviewed by whom?”

Done by hand, that question is answered by a commit message. Here it is answered by a transcript, a named override intent, a measured contrast ratio and a review record — for every hop, every time.

The audit artefact is a by-product of the work, not a document written afterwards.

The pilot

Two weeks · one repository · one named design-system owner

  • Week 1 — land the intent gate on the real library, run 14→15 on a branch, open three consumer PRs.
  • Week 2 — run the next hop, measure reviewer minutes per PR, publish the refusal rate.
  • Success — n consumer PRs merged with no baseline regenerated without a written reason.
  • Failure we would accept — it stops more often than it ships, and the transcripts tell you exactly why.
